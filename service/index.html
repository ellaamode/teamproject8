01 · 문제

규제 정보는 업무와 가장 가깝지만, 가장 찾기 어렵습니다

금융회사 실무에서 가장 큰 제약 중 하나는 규제입니다. 그런데 ‘이 업무를 해도 되나’에 답하려면 여러 사이트를 오가며 법령과 해석 자료를 하나씩 찾아, 어떤 해석이 어느 조문에 관한 것인지 직접 맞춰 봐야 합니다.

STEP 1

자료가 여러 곳에 흩어져 있다

법령과 행정규칙은 국가법령정보센터, 법령해석·비조치의견·행정지도는 금융규제·법령해석포털에 따로 있습니다. 둘 사이를 잇는 화면은 없습니다.

STEP 2

해석에 대상 조문이 연결되어 있지 않다

법령해석·비조치의견 회신 6,177건에는 ‘관련 조문’ 칸이 없습니다. 본문 속 인용도 「자본시장과 금융투자업에 관한 법률」 제9조, 자본시장법 제9조, 같은 법 시행령 제7조처럼 제각각입니다.

STEP 3

바뀌는 내용을 미리 알기 어렵다

개정된 조문은 시행일 전까지 지금 본문과 앞으로 바뀔 본문이 함께 있습니다(대상 법령 중 71개 조문). 행정지도도 존속기간이 끝나면 효력을 잃습니다. 이런 변화가 한곳에 모여 있지 않아, 직접 찾아보지 않으면 놓치기 쉽습니다.

02 · 사용자

“이 조문, 지금 어떻게 해석되고 앞으로 어떻게 바뀌나”

주 사용자는 금융회사에서 규제를 직접 확인해야 하는 실무자입니다. 법률 자문을 대신하지 않고, 판단 전에 확인해야 할 자료를 빠짐없이 모아 주는 조회 도구입니다.

03 · 핵심 아이디어

모든 자료의 기준점은 ‘조문’입니다

자료를 유형별 게시판으로 나열하지 않고, 조문을 중심에 두고 엮습니다. 위로는 근거 법률, 아래로는 위임받은 시행령·감독규정, 옆으로는 그 조문을 인용한 법령해석·비조치의견·행정지도가 연결됩니다. 아래 그림은 자본시장법 제42조(금융투자업자의 업무위탁)의 실제 데이터이고, 오른쪽 문서는 이 조문을 인용한 실제 회신의 제목을 줄여 쓴 것입니다. 서비스의 조문 화면에서는 같은 형태의 그림이 실제 데이터로 자동으로 그려집니다.

조문마다 고유 번호

fscma:42(자본시장법 제42조)처럼 법령과 조문 번호로 만든 고유 번호를 씁니다. 본문이 개정돼도 번호는 그대로이고, 본문만 시행일별로 쌓입니다.

위·아래로: 위임 관계

법률 조문을 열면 위임받은 시행령·감독규정 조문이, 시행령 조문을 열면 근거가 된 법률 조문이 보입니다. 실무의 세부 기준은 대개 하위 규정에 있습니다.

옆으로: 인용한 자료

법령해석·비조치의견·행정지도가 어느 조문을 다뤘는지 본문에서 찾아 연결합니다. 어떤 표현을 보고 연결했는지와 확실한 정도를 함께 남깁니다.

07 · 시스템 구조

모으는 일과 보여 주는 일을 나눴습니다

GitHub Actions의 수집 프로그램이 매일 아침(06:00 예약) 법제처 Open API와 금융위 포털에서 새 자료를 받아, 정리·조문 연결·변화 기록까지 계산한 뒤 결과를 Supabase(PostgreSQL 데이터베이스)에 저장합니다. 화면에 보여 주는 API(FastAPI)는 이렇게 저장된 데이터를 읽기만 합니다. 사용자가 화면을 볼 때 원천 사이트에 요청이 가지 않으므로 무료 서버에서도 빠르고, 원천 사이트에 부담을 주지 않습니다. 외부 원천과의 연결 결과(원천별 수집 방식·건수·마지막 수집 시각·실행 기록)는 GET /collection으로 Swagger에서 바로 확인할 수 있습니다.

받은 원문은 그대로 보관

원천에서 받은 내용을 고치지 않고 저장해 두고, 그것을 정리해서 씁니다. 연결 규칙을 고쳐도 원천 사이트에 다시 요청하지 않고 저장된 원문으로 다시 계산합니다.

바뀐 것만, 몇 번 돌려도 같게

새 글이나 내용이 바뀐 글만 처리합니다. 같은 작업을 두 번 실행해도 데이터가 중복으로 쌓이지 않습니다(실제로 확인).

조문은 시행일별로 보관

지금 시행 중인 본문과 앞으로 시행될 본문을 함께 저장하고, 각 본문이 언제부터 언제까지 효력이 있는지 계산합니다. 아직 시행 전인 신설 조문은 현행으로 보이지 않습니다.

연결에는 근거를 함께

모든 연결에 원문의 어느 표현을 보고 연결했는지와 그 확실한 정도를 남겨, 화면에서 “왜 이 조문과 연결됐는지”를 보여 줍니다.

변화는 한곳에 기록

새 해석, 조문 개정·시행 예정, 행정지도 시행·만료를 한 표에 날짜와 함께 쌓습니다. 홈의 ‘최근 변화’와 관심 조문 화면이 같은 기록을 씁니다.

멈추지 않는 화면

서버가 응답하지 않으면 미리 저장해 둔 대표 데이터로 자동으로 바꿔 보여 줍니다. 무료 서버가 잠들어 있어도 화면은 멈추지 않습니다.

요청 한 번은 이렇게 처리됩니다: 조문 카드를 열 때

① 화면 (Vercel)

조문 카드를 열면 화면이 GET /articles/fscma:42를 요청

② 조회 API (Render)

30분 안에 같은 요청이 있었으면 기억해 둔 응답을 바로 돌려줌 (약 0.3초)

③ DB (Supabase)

처음이면 조회 전용 계정으로 시행일별 본문·위임 관계·인용 연결·변화 기록을 SQL로 읽음 (약 3.4초)

④ 응답

JSON으로 돌려주고, 다음 요청을 위해 서버가 30분 동안 기억

⑤ 화면 그리기

본문·위임·해석을 보여 주고 연결 지도를 자동으로 그림. 7초 넘게 답이 없으면 저장된 데이터로 먼저 표시

기술 선택과 이유

선택이유와 결과
화면은 React 없이 HTML·CSS·JavaScript로 직접 구현과제 가이드가 허용하는 방식입니다. 이 서비스의 핵심은 백엔드와 데이터라서 화면은 가볍게 유지했습니다. 빌드 과정이 없어 Vercel에 폴더째로 배포하고, 서버가 잠들어도 미리 저장해 둔 데이터로 바로 동작합니다.
조회 API에 서버 캐시와 미리 준비Render 서버(미국 오리건)와 Supabase DB(서울)가 멀어 DB 질의 한 번에 왕복 시간이 0.3~0.4초 걸렸고, 질의가 많은 화면은 8초가 넘었습니다. 데이터는 하루 한 번만 바뀌므로 같은 요청의 응답을 서버가 30분 동안 기억하고, 서버가 켜질 때 첫 화면들의 응답을 미리 만들어 둡니다. 데이터 분석은 8.5초에서 0.6초로, 조문 카드는 다시 열 때 3.4초에서 0.3초로 줄었습니다.
화면은 7초까지만 기다림무료 서버는 15분간 요청이 없으면 잠들고, 깨는 데 30~60초가 걸립니다. 7초 안에 답이 없으면 저장된 데이터로 먼저 보여 주고, 서버가 깨어나면 다음 화면부터 실시간 데이터로 돌아갑니다.

수집은 왜 GitHub Actions에서 하나

GitHub은 과제 가이드가 정한 소스 코드 관리 플랫폼이고, Actions는 그 저장소에 들어 있는 실행 기능입니다. 수집 코드(service/backend/batch)와 실행 설정(.github/workflows/collect.yml)이 같은 저장소에 있어서 서버를 하나 더 빌릴 필요가 없습니다. 매일 수집하려면 아래 네 가지가 필요했고, 무료 요금제 안에서 넷을 모두 채우는 곳이 Actions였습니다.

매일 수집에 필요한 것Render 무료 서버(FastAPI)에서 하면GitHub Actions에서 하면
정해진 시간에 자동 실행무료 요금제에는 예약 실행(Cron Job)이 없음예약 실행 기본 제공 — 매일 06:00, 필요하면 버튼으로도 실행
오래 걸리는 작업15분간 요청이 없으면 잠들고, 메모리 512MB를 조회와 나눠 씀실행할 때마다 GitHub이 빌려주는 임시 가상 컴퓨터에서 한 번에 최대 6시간까지 실행 (끝나면 그 컴퓨터는 사라짐)
공개 서버에 쓰기 기능을 열지 않기‘수집 시작’ API(POST)와 DB 쓰기 계정을 인터넷에 열린 서버에 둬야 함공개 서버(Render)에는 조회(GET)와 읽기 계정만, 쓰기 계정은 Actions에만
비용 0원예약 실행을 쓰려면 유료공개 저장소는 무료

조회가 느려지지 않는다

수집과 조회가 서로 다른 컴퓨터에서 돌아서, 수집하는 동안에도 화면 응답 속도가 그대로입니다.

공개 서버가 뚫려도 데이터는 안전

인터넷에 열린 Render에는 읽기 계정만 있어서, 연결 정보가 새도 데이터를 바꾸거나 지울 수 없습니다. 계정 구성은 12 운영·보안에서 설명합니다.

무료 DB가 잠들지 않는다

Supabase 무료 프로젝트는 일주일간 사용이 없으면 일시정지됩니다. 매일 수집이 DB에 실행 기록을 쓰므로 방문자가 없는 주에도 멈추지 않습니다.

실패해도 서비스는 계속

원천 사이트가 막히거나 수집이 실패해도 화면은 마지막으로 모은 데이터를 계속 보여 줍니다. 실패는 실행 기록과 GitHub 알림 메일로 바로 알 수 있습니다.

외부 연동을 Swagger로 확인

원천별 수집 방식·건수·마지막 수집 시각·최근 실행 결과를 GET /collection이 돌려줍니다. 수집이 화면 밖에서 돌아도 API로 바로 확인할 수 있습니다.

원천 사이트에 하루 한 번만

사용자가 몇 명이든 법제처·금융위 포털에는 하루 한 번, 새로 생긴 것만 요청합니다. 사용자 수가 늘어도 원천 사이트 부담은 늘지 않습니다.

09 · 인용 조문 자동 연결

서비스의 핵심 기술: 본문에서 ‘어느 법 몇 조’를 찾는다

실제 결과 (회신 6,177건)

대상 5개 법률을 언급한 회신 2,730건 중 2,112건(77.4%)을 조문까지 연결했습니다(연결 5,037개). 회신 전체로 보면 2,152건(34.8%)인데, 나머지 대부분이 여신전문금융업법·대부업법처럼 아직 대상에 넣지 않은 법령을 인용하기 때문입니다. 이 ‘대상 밖 법령’ 기록이 곧 2단계 확대 순서의 근거가 됩니다.

정확도(맞게 연결된 비율): 무작위로 뽑은 연결 100개를 원문과 하나씩 대조했습니다. 처음 87%였고, 틀린 13건의 원인을 ‘애매하면 보류’ 규칙으로 막은 뒤 새로 뽑은 100개에서 96%가 됐습니다. 연결 수는 5,266개에서 5,037개로 줄었지만, 대상 법령 언급 회신의 연결률은 77.4%로 그대로입니다. 틀렸던 사례는 모두 자동 테스트로 남겨 규칙을 고칠 때마다 다시 확인합니다(테스트 60개).

수집 프로그램은 batch_writer(쓰기), API는 api_reader(읽기, 쿼리당 5초 제한)로 접속합니다. 모든 표에 행 수준 보안(RLS)을 켜고, API는 Vercel 화면 주소에서 온 요청만 받습니다(CORS).

같은 사이트에는 1.5초 간격으로, 새 글만 요청하고, 요청에 우리 연락처를 밝힙니다. 사이트가 403·429로 거부하면 즉시 멈추고 기록합니다. 모든 문서에 원문 출처 링크를 답니다. 포털 저작권정책의 링크 통지는 정식 공개 전에 이행합니다.

        
개인정보를 모으지 않는다
로그인이 없고, 관심 조문은 사용자 브라우저에만 저장합니다. 수집한 원문에 들어 있던 전화번호·담당 공무원 실명, 행정지도 등록자 이름은 저장하기 전에 가립니다.

      

    


    
DB 접속 계정: 용도별 역할(role) 분리 — 최소 권한 원칙

    
이 서비스는 DB를 쓰는 프로그램이 둘입니다. 인터넷에 공개된 조회 API는 읽기만, 수집 프로그램은 쓰기만 합니다. 그래서 같은 PostgreSQL 안에 접속 계정(역할)을 셋으로 나누고, 각자 맡은 일에 필요한 권한만 주었습니다(최소 권한 원칙).

    

      
역할(role)누가 쓰나권한(GRANT)과 제한언제

      
postgres사람(관리자)전부 — 테이블 생성·변경·삭제(DDL) 포함처음 스키마 만들 때, 초기 데이터 적재 1회

      
batch_writer수집 프로그램 (GitHub Actions)SELECT·INSERT·UPDATE·DELETE만. 표 구조는 못 바꿈. 집계 다시 계산은 미리 만들어 둔 함수(SECURITY DEFINER)로만수집을 실행할 때

      
api_reader조회 API (FastAPI · Render)SELECT만. 원문 보관 표(raw_payloads)는 읽기도 불가. 쿼리당 5초 제한(statement_timeout)사용자가 화면을 볼 때마다

    

    

      
피해 범위를 줄인다
공격받기 쉬운 곳은 인터넷에 열린 Render 서버입니다. 그 연결 정보가 새거나 코드에 허점이 있어도 api_reader로는 이미 공개된 데이터를 읽는 것밖에 못 합니다. 관리자 계정이었다면 테이블 삭제까지 가능합니다.

      
실수를 DB가 막는다
조회 API 코드에 데이터를 바꾸는 줄이 실수로 들어가도 DB가 권한 오류로 거부합니다. 실제로 조회 계정으로 전체 API를 시험해 권한이 빠진 테이블 2개를 찾아 고쳤습니다 — 분리가 실제로 지켜진다는 증거입니다.

      
무료 DB를 지킨다
무거운 검색이 DB를 오래 붙잡지 못하게 조회 계정에만 5초 제한을 걸었습니다. 모든 테이블에 행 수준 보안(RLS)을 켜고, Supabase 자동 API(Data API)는 쓰지 않아 꺼 두었습니다.

    


    
수업 실습(4주차 워크북) 방식과의 차이

    
개발 환경(FastAPI · Supabase PostgreSQL · Render · Vercel · GitHub)은 가이드 그대로입니다. 다만 수업의 가계부 API와 서비스 구조가 달라, 아래 네 가지는 다르게 설계했습니다. 모두 가이드가 정한 범위 안의 선택입니다.

    

      
항목수업 실습 (가계부 API)이 프로젝트이유

      
DB를 쓰는 프로그램FastAPI 앱 하나가 읽기·쓰기 모두 (POST로 저장, GET으로 조회)조회 API는 읽기만, 쓰기는 수집 프로그램만사용자는 조회만 하고, 데이터는 공공 원천에서 매일 자동으로 들어오는 서비스이기 때문

      
DB 접속 계정관리자 postgres 하나를 모든 곳에역할 셋으로 분리 (위 표)최소 권한 원칙 — 공개 서버에는 읽기 권한만

      
테이블 생성ORM(SQLAlchemy) 클래스 + 앱 시작 시 create_all()SQL 스크립트(001_schema.sql)를 SQL Editor에서 실행, DB 접근은 드라이버(psycopg)로 SQL 직접 실행계정 권한·행 수준 보안·집계 뷰처럼 ORM으로 표현하기 어려운 DB 기능을 쓰고, 조회 API에는 표를 만들 권한 자체가 없기 때문

      
비밀값 관리로컬 .env + Render 환경변수Render 환경변수 + GitHub Actions Secrets (로컬 1회 작업은 화면에 안 보이는 입력)원칙은 같음 — 연결 문자열은 코드·저장소에 두지 않는다
