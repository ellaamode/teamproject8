01 · 문제

규제 정보는 업무와 가장 가깝지만, 가장 찾기 어렵습니다

금융회사 실무에서 가장 큰 제약 중 하나는 규제입니다. 그런데 ‘이 업무를 해도 되나’에 답하려면 여러 사이트를 오가며, 서로 연결되지 않은 자료를 사람이 직접 이어 붙여야 합니다.

STEP 1

자료가 여러 곳에 흩어져 있다

법령과 하위법령은 국가법령정보센터, 법령해석·비조치의견·행정지도는 금융규제·법령해석포털에 따로 있습니다. 둘 사이를 잇는 화면은 없습니다.

STEP 2

해석은 조문과 이어져 있지 않다

법령해석·비조치의견 회신 6,174건에는 ‘관련 조문’ 칸이 없습니다. 본문 속 인용도 「자본시장과 금융투자업에 관한 법률」 제9조, 자본시장법 제9조, 같은 법 시행령 제7조처럼 제각각입니다.

STEP 3

변화는 소리 없이 온다

한 조문에 지금 본문과 앞으로 바뀔 본문이 함께 있고(대상 법령 전체 71개 조문), 행정지도는 존속기간이 끝나면 효력을 잃습니다. 직접 찾아보기 전에는 알 수 없습니다.

02 · 사용자

“이 조문, 지금 어떻게 해석되고 앞으로 어떻게 바뀌나”

주 사용자는 금융회사에서 규제를 직접 확인해야 하는 실무자입니다. 법률 자문을 대신하지 않고, 판단 전에 확인해야 할 자료를 빠짐없이 모아 주는 조회 도구입니다.

03 · 핵심 아이디어

모든 자료의 기준점은 ‘조문’입니다

자료를 유형별 게시판으로 나열하지 않고, 조문을 중심에 두고 엮습니다. 위로는 근거 법률, 아래로는 위임받은 시행령·감독규정, 옆으로는 그 조문을 인용한 법령해석·비조치의견·행정지도가 연결됩니다. 아래 그림의 조문과 위임 관계는 실제 데이터이고, 오른쪽 문서 제목만 설명용 예시입니다. 서비스의 조문 화면에서는 같은 형태의 그림이 실제 데이터로 자동으로 그려집니다.

조문마다 고유 번호

efta:25의2(전자금융거래법 제25조의2)처럼 법령과 조문 번호로 만든 고유 번호를 씁니다. 본문이 개정돼도 번호는 그대로이고, 본문만 시행일별로 쌓입니다.

위·아래로: 위임 관계

법률 조문을 열면 위임받은 시행령·감독규정 조문이, 시행령 조문을 열면 근거가 된 법률 조문이 보입니다. 실무의 세부 기준은 대개 하위 규정에 있습니다.

옆으로: 인용한 자료

법령해석·비조치의견·행정지도가 어느 조문을 다뤘는지 본문에서 찾아 연결합니다. 어떤 표현을 보고 연결했는지와 확실한 정도를 함께 남깁니다.

법령 조문은 국가법령정보센터의 실제 조문(저작권법 제7조상 보호받지 않는 저작물), 회신사례·행정지도는 금융규제·법령해석포털에서 수집한 원문입니다. 원문은 고치지 않고 저장하며 모든 문서에 출처 링크를 답니다. 수업 시연 목적이며, 정식 공개 전에는 포털 저작권정책에 따른 협의가 필요합니다.

세 데이터 모두 같은 순서로 처리

받은 원문을 raw_payloads에 그대로 보관한 뒤, 정리 → 조문 연결 → 변화 기록 순서로 가공합니다. 원문을 보관해 두므로 원천 사이트에 다시 요청하지 않고도 언제든 처음부터 다시 가공할 수 있습니다(실제로 Supabase에 이렇게 옮겨 담았습니다).

06 · 시스템 구조

모으는 일과 보여 주는 일을 나눴습니다

데이터를 모아 정리하는 일은 수집 프로그램(GitHub Actions)이 따로 하고, 화면에 보여 주는 API(FastAPI)는 정리된 데이터를 읽기만 합니다. 사용자가 화면을 볼 때 원천 사이트에 요청이 가지 않으므로 무료 서버에서도 빠르고, 원천 사이트에 부담을 주지 않습니다. 외부 원천과의 연결 결과(원천별 수집 방식·건수·마지막 수집 시각·실행 기록)는 GET /collection으로 Swagger에서 바로 확인할 수 있습니다.

받은 원문은 그대로 보관

원천에서 받은 내용을 고치지 않고 저장해 두고, 그것을 정리해서 씁니다. 연결 규칙을 고쳐도 원천 사이트에 다시 요청하지 않고 저장된 원문으로 다시 계산합니다.

바뀐 것만, 몇 번 돌려도 같게

새 글이나 내용이 바뀐 글만 처리합니다. 같은 작업을 두 번 실행해도 데이터가 중복으로 쌓이지 않습니다(실제로 확인).

조문은 시행일별로 보관

지금 시행 중인 본문과 앞으로 시행될 본문을 함께 저장하고, 각 본문이 언제부터 언제까지 효력이 있는지 계산합니다. 아직 시행 전인 신설 조문은 현행으로 보이지 않습니다.

연결에는 근거를 함께

모든 연결에 원문의 어느 표현을 보고 연결했는지와 그 확실한 정도를 남겨, 화면에서 “왜 이 조문과 연결됐는지”를 보여 줍니다.

변화는 한곳에 기록

새 해석, 조문 개정·시행 예정, 행정지도 시행·만료를 한 표에 날짜와 함께 쌓습니다. 홈의 ‘최근 변화’와 관심 조문 화면이 같은 기록을 씁니다.

멈추지 않는 화면

서버가 응답하지 않으면 미리 저장해 둔 대표 데이터로 자동으로 바꿔 보여 줍니다. 무료 서버가 잠들어 있어도 화면은 멈추지 않습니다.

08 · 인용 연결 엔진

09 · 데이터베이스

표 10개와 집계 1개를 세 층으로 나눴습니다

DB 테이블 문서 전체 보기 (컬럼·PK·FK)

① 원문·운영 층은 수집 프로그램만 쓰는 보관함이고, ② 정리 층은 원천의 내용을 법령·조문·문서로 나눠 담은 것이며, ③ 연결·변화 층은 서비스가 계산해 만든 연결과 변화 기록입니다. ③은 언제든 지우고 ②에서 다시 계산할 수 있습니다.

데이터 규모 (1단계: 5개 법률 + 하위법령 21건)

  • 조문 3,629개 · 문서 6,341건(회신 6,174 + 행정지도 167) · 조문 연결 5,266개
  • 회신은 해마다 수백 건씩 늘어남 · 2단계 확대 시 조문 약 5,000개
  • DB 전체 약 81MB(실측) → Supabase 무료 한도(500MB) 안

검색 인덱스

PostgreSQL 기본 검색은 한국어 단어를 잘게 나누지 못합니다. 그래서 pg_trgm(글자 세 개씩 묶어 찾는 색인)으로 단어 일부만 입력해도 찾게 했습니다. 규모가 커지면 Supabase가 지원하는 한국어 검색 확장(PGroonga)으로 바꿀 수 있습니다.

수집 프로그램은 batch_writer(쓰기), API는 api_reader(읽기, 쿼리당 5초 제한)로 접속합니다. 모든 표에 행 수준 보안(RLS)을 켜고, API는 Vercel 화면 주소에서 온 요청만 받습니다(CORS).

        
원천 사이트 배려·출처
같은 사이트에는 1.5초 간격으로, 새 글만 요청하고, 요청에 우리 연락처를 밝힙니다. 사이트가 403·429로 거부하면 즉시 멈추고 기록합니다. 모든 문서에 원문 출처 링크를 답니다. 포털 저작권정책의 링크 통지는 정식 공개 전에 이행합니다.

        
개인정보를 모으지 않는다
로그인이 없고, 관심 조문은 사용자 브라우저에만 저장합니다. 수집한 원문에 들어 있던 전화번호·담당 공무원 실명, 행정지도 등록자 이름은 저장하기 전에 가립니다.

      

    


    
DB 접속 계정: 용도별 역할(role) 분리 — 최소 권한 원칙

    
이 서비스는 DB를 쓰는 프로그램이 둘입니다. 인터넷에 공개된 조회 API는 읽기만, 수집 프로그램은 쓰기만 합니다. 그래서 같은 PostgreSQL 안에 접속 계정(역할)을 셋으로 나누고, 각자 맡은 일에 필요한 권한만 주었습니다(최소 권한 원칙).

    

      
역할(role)누가 쓰나권한(GRANT)과 제한언제

      
postgres사람(관리자)전부 — 테이블 생성·변경·삭제(DDL) 포함처음 스키마 만들 때, 초기 데이터 적재 1회

      
batch_writer수집 프로그램 (GitHub Actions)SELECT·INSERT·UPDATE·DELETE만. 표 구조는 못 바꿈. 집계 다시 계산은 미리 만들어 둔 함수(SECURITY DEFINER)로만수집을 실행할 때

      
api_reader조회 API (FastAPI · Render)SELECT만. 원문 보관 표(raw_payloads)는 읽기도 불가. 쿼리당 5초 제한(statement_timeout)사용자가 화면을 볼 때마다

    

    

      
피해 범위를 줄인다
공격받기 쉬운 곳은 인터넷에 열린 Render 서버입니다. 그 연결 정보가 새거나 코드에 허점이 있어도 api_reader로는 이미 공개된 데이터를 읽는 것밖에 못 합니다. 관리자 계정이었다면 테이블 삭제까지 가능합니다.

      
실수를 DB가 막는다
조회 API 코드에 데이터를 바꾸는 줄이 실수로 들어가도 DB가 권한 오류로 거부합니다. 실제로 조회 계정으로 전체 API를 시험해 권한이 빠진 테이블 2개를 찾아 고쳤습니다 — 분리가 실제로 지켜진다는 증거입니다.

      
무료 DB를 지킨다
무거운 검색이 DB를 오래 붙잡지 못하게 조회 계정에만 5초 제한을 걸었습니다. 모든 테이블에 행 수준 보안(RLS)을 켜고, Supabase 자동 API(Data API)는 쓰지 않아 꺼 두었습니다.

    


    
수업 실습(4주차 워크북) 방식과의 차이

    
개발 환경(FastAPI · Supabase PostgreSQL · Render · Vercel · GitHub)은 가이드 그대로입니다. 다만 수업의 가계부 API와 서비스 구조가 달라, 아래 네 가지는 다르게 설계했습니다. 모두 가이드가 정한 범위 안의 선택입니다.

    

      
항목수업 실습 (가계부 API)이 프로젝트이유

      
DB를 쓰는 프로그램FastAPI 앱 하나가 읽기·쓰기 모두 (POST로 저장, GET으로 조회)조회 API는 읽기만, 쓰기는 수집 프로그램만사용자는 조회만 하고, 데이터는 공공 원천에서 매일 자동으로 들어오는 서비스이기 때문

      
DB 접속 계정관리자 postgres 하나를 모든 곳에역할 셋으로 분리 (위 표)최소 권한 원칙 — 공개 서버에는 읽기 권한만

      
테이블 생성ORM(SQLAlchemy) 클래스 + 앱 시작 시 create_all()SQL 스크립트(001_schema.sql)를 SQL Editor에서 실행, DB 접근은 드라이버(psycopg)로 SQL 직접 실행계정 권한·행 수준 보안·집계 뷰처럼 ORM으로 표현하기 어려운 DB 기능을 쓰고, 조회 API에는 표를 만들 권한 자체가 없기 때문

      
비밀값 관리로컬 .env + Render 환경변수Render 환경변수 + GitHub Actions Secrets (로컬 1회 작업은 화면에 안 보이는 입력)원칙은 같음 — 연결 문자열은 코드·저장소에 두지 않는다

    

    
연결 문자열 형식 주의
      
수업은 SQLAlchemy용으로 앞머리를 postgresql+psycopg://로 바꾸지만, 이 프로젝트는 드라이버를 직접 쓰므로 Supabase에서 복사한 postgresql:// 그대로 씁니다(Session pooler, 포트 5432). 아이디 자리만 역할에 맞게 batch_writer.[프로젝트ID] · api_reader.[프로젝트ID]로 바꿉니다.

13 · 위험과 대응

    
잘못 연결하는 것보다, 연결하지 않는 편이 낫다

    

      
위험영향대응

      
포털이 공식 API가 아님화면 변경 시 수집 중단받은 화면에 꼭 있어야 할 항목(‘질의요지’ 등)이 없으면 즉시 실패로 기록, 사이트가 거부(403·429)하면 그 사이트 수집을 바로 멈춤. 이미 받은 데이터는 그대로 서비스

      
법제처 Open API 장애·키 문제그날 법령 갱신 누락받아 둔 조문은 그대로 유지, API가 전부 실패한 날만 웹페이지 수집으로 대체 · 실행 기록으로 확인

      
잘못된 조문 연결엉뚱한 선례를 보여 줌실제로 없는 조문은 연결 안 함, 연결 근거와 확실한 정도를 화면에 표시, 사람이 검수한 연결은 다시 계산해도 유지

      
조문 번호 이동(개정)옛 해석이 지금의 다른 조문에 붙음문서 날짜 기준 버전 대조를 2단계 과제로, 그 전까지는 화면에 회신일을 항상 함께 표시

      
법률 자문으로 오해책임 문제“조회 도구이며 법률 자문이 아님” 고정 안내, 원문 링크 필수, 요약·추천 표현 없음

      
무료 서버 잠듦첫 화면 30~60초대표 데이터로 자동 전환(구현됨), 발표 전 /health 호출로 깨움

법령·회신 원문은 계속 무료로 두고 출처 링크를 답니다. 유료는 우리가 만든 연결·알림·연동 기능에만 붙입니다. 금융위 포털 데이터는 상용화 전에 이용 협의와 공식 API 제공 요청을 먼저 합니다.

      
단계
        
1단계(지금) 무료 공개, 데이터와 연결 정확도 검증 → 2단계 준법감시 실무 2~3팀에 관심 조문 알림 시범, 실제 확인 빈도와 지불 의향 측정 → 3단계 팀 구독·연동 API, 대상 법령 확대
