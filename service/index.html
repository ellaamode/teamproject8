01 · 문제

규제 정보는 업무와 가장 가깝지만, 가장 찾기 어렵습니다

금융회사 실무에서 기술 이슈를 빼면 가장 큰 제약은 규제입니다. 그런데 ‘이 업무를 해도 되나’에 답하려면 서로 다른 다섯 곳을 오가며, 서로 연결되지 않은 자료를 사람이 직접 이어 붙여야 합니다.

STEP 1

자료가 다섯 곳에 흩어져 있다

법령·감독규정은 국가법령정보센터, 해석·비조치의견·금융위 행정지도는 금융규제·법령해석포털, 금감원 행정지도는 금감원 홈페이지, 의원 입법예고는 국회에 있습니다.

STEP 2

해석은 조문과 이어져 있지 않다

법령해석·비조치의견 회신 6,174건에는 ‘관련 조문’ 칸이 없습니다. 본문 속 인용도 「여신전문금융업법」 제2조제3호, 여전법 제2조제5호, 통신사기피해환급법 2조의4 1항처럼 제각각입니다.

STEP 3

변화는 소리 없이 온다

같은 조문에 현행 본문과 시행예정 본문이 함께 존재하고(전자금융거래법 14개 조문), 행정지도는 존속기간이 끝나면 효력을 잃습니다. 직접 찾아보기 전에는 알 수 없습니다.

우리 아이디어 피칭의 예시도 틀려 있었습니다

피칭에서는 ‘전자금융거래법 제23조 선불충전금의 관리’를 예로 들었지만, 현행법(2026.10.02 시행)에서 제23조는 ‘전자지급수단 등의 발행과 이용한도’이고, 선불충전금은 제25조의2·제25조의3입니다. 조문 번호와 내용은 개정으로 바뀝니다. 그래서 이 서비스는 조문을 시행일 기준 버전으로 관리합니다.

03 · 핵심 아이디어

모든 자료의 기준점은 ‘조문’입니다

자료를 유형별 게시판으로 나열하지 않고, 조문을 중심에 두고 엮습니다. 위로는 근거 법률, 아래로는 위임받은 시행령·감독규정, 옆으로는 그 조문을 인용한 해석·비조치의견·행정지도·예고가 연결됩니다. 아래 그림은 설명용 예시입니다(오른쪽 문서 제목은 예시). 서비스의 조문 화면에서는 같은 형태의 그림이 실제 데이터로 자동 생성됩니다.

조문 = 하나의 주소

efta:25의2처럼 법령과 조문 번호로 고정된 키를 씁니다. 본문이 개정돼도 키는 같고, 본문은 시행일별 버전으로 쌓입니다.

위·아래로: 위임 관계

법률 조문을 열면 위임받은 시행령·감독규정 조문이, 시행령 조문을 열면 근거 법률 조문이 보입니다. 실무 기준은 대개 하위 규정에 있습니다.

옆으로: 인용한 자료

해석·비조치의견·행정지도·예고가 어느 조문을 다뤘는지 본문에서 찾아 연결합니다. 근거 표현과 신뢰도를 함께 남깁니다.

법령 조문은 국가법령정보센터의 실제 조문(저작권법 제7조상 보호받지 않는 저작물), 회신사례·행정지도는 금융규제·법령해석포털에서 수집한 원문입니다. 원문은 고치지 않고 저장하며 모든 문서에 출처 링크를 답니다. 수업 시연 목적이며, 정식 공개 전에는 포털 저작권정책에 따른 협의가 필요합니다.

수집 → 가공은 모두 같은 파이프라인

원문을 raw_payloads에 그대로 보관하고 정규화 → 인용 연결 → 변화 이벤트를 만듭니다. 수집한 원본은 파일로 옮겨 Supabase에서 그대로 다시 가공할 수 있습니다(재수집 불필요).

06 · 시스템 구조

쓰기는 배치만, 읽기는 API만

수집·가공은 하루 한 번 배치가 하고, API는 이미 정리된 데이터를 읽기만 합니다. 사용자 요청이 원천 서버에 닿지 않으므로 무료 서버에서도 빠르고, 원천에 부담을 주지 않습니다.

원본 먼저, 가공은 나중

원천 응답을 그대로 보관하고 그 위에서 가공합니다. 인용 규칙을 고치면 원천을 다시 긁지 않고 link --all만 다시 돌립니다.

증분·멱등

내용 해시로 바뀐 것만 처리하고, 모든 쓰기는 자연키 UPSERT입니다. 같은 날 두 번 돌려도 결과가 같은 것을 실제로 확인했습니다.

조문은 시행일 버전

현행과 시행예정 본문을 함께 저장하고, 각 버전의 효력 구간을 계산합니다. 시행예정만 있는 신설 조문은 현행으로 보이지 않게 합니다.

연결에는 근거와 신뢰도

모든 링크에 원문 표현·해석 방법·신뢰도를 남겨, 화면에서 “왜 이 조문과 연결됐는지”를 보여 줍니다.

변화는 이벤트로

새 해석·개정·행정지도 만료를 한 테이블에 쌓아, 홈 피드와 관심 조문 모니터링이 같은 데이터를 씁니다.

멈추지 않는 화면

API가 응답하지 않으면 실제 API 응답을 떠 둔 스냅숏으로 자동 전환합니다. 발표 시연 중 서버가 잠들어도 화면은 동작합니다.

09 · 데이터베이스

테이블 10개 + 집계 뷰 1개, 세 층으로 나눴습니다

DB 테이블 문서 전체 보기 (컬럼·PK·FK)

원본·운영 층은 배치만 보고, 정규화 층은 원천의 내용을 구조화하며, 파생 층은 서비스가 만든 연결과 변화입니다. 파생 층은 언제든 지우고 다시 만들 수 있습니다.

데이터 규모 (1단계: 5개 법률 + 하위법령 21건)

  • 조문 3,629개(실측) · 2단계 확대 시 약 5,000개
  • 회신사례 약 12,100건 + 연 600~800건 증가 · 행정지도 수백 건
  • 본문 텍스트 약 60~80MB + 인덱스 → Supabase 무료 한도(500MB) 안

검색 인덱스

한국어는 PostgreSQL 기본 전문검색이 형태소를 나누지 못해, pg_trgm(3글자 조각) GIN 인덱스로 부분일치·유사도 검색을 합니다. 규모가 커지면 Supabase가 지원하는 PGroonga로 바꿀 수 있습니다.

회신 원문(질의요지·회답·이유)에서 인용 연결 엔진으로 조문을 찾아 집계했습니다. 하위법령(시행령·시행규칙·감독규정·고시·시행세칙) 인용은 모법으로 합산하고, 같은 회신이 한 법령을 여러 번 인용해도 1건으로 셉니다. 회신일은 포털 등록일 기준입니다.

  


  
  

    
15 · 비즈니스 모델

    
공공 데이터로 만드는, 운영비 0원의 규제 인프라

    
기본은 누구나 무료로 쓰는 공공 서비스입니다. 운영비가 거의 들지 않는 구조로 지속 가능성을 확보하고, 수익화는 기업용 확장 기능에서 향후 검토합니다.

    

      
대상 고객
    
        
  • 1차: 금융회사 준법감시·법무·상품기획·IT보안 실무자 (은행·카드·증권·보험·전자금융업자·핀테크)
    • 
        
  • 2차: 전담 법무 조직이 없는 핀테크 스타트업, 금융 전문 법무법인·컨설팅
    • 
        
  • 3차: 금융규제를 공부하는 학생·연구자

      
제공 가치
    
        
  • 시간: 5곳에 흩어진 규제 자료를 조문 하나에서 확인
    • 
        
  • 누락 방지: 법→시행령→감독규정 위임과 그 조문을 다룬 선례를 함께 제시
    • 
        
  • 변화 감지: 시행 예정 조문, 행정지도 만료, 새 해석을 관심 조문 기준으로 모아 줌
    • 
        
  • 신뢰: 모든 연결에 근거 표현·신뢰도, 모든 문서에 원문 링크

      
지속 가능한 운영 방안
    
        
  • 운영비 0원 구조: Vercel·Render·Supabase·GitHub 무료 한도 안 (데이터 약 100MB, 하루 1회 수집)
    • 
        
  • 사람이 거의 필요 없는 운영: 수집·가공·연결이 매일 자동, 실패는 실행 기록으로 확인
    • 
        
  • 공공 데이터 협력: 금융위 포털 데이터의 공식 API 제공을 요청해 크롤링 의존도를 낮춤
    • 
        
  • 오픈소스 공개: 별칭 사전·인용 규칙을 실무자 기여로 함께 개선

    

    
향후 수익 가능성 (검토 단계)
      
무료 조회는 그대로 두고, 기업이 필요로 하는 부가 기능(사내 시스템 연동용 API, 관심 조문 이메일 알림, 팀 단위 공유·검수 기록)을 기업 대상 유료 서비스로 제공하는 방안을 검토할 수 있습니다. 이 단계에서는 요금을 정하지 않았습니다.
